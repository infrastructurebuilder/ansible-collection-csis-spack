# Feature Specification: Repeat runs that do nothing, and say so

**Feature Branch**: `feature/coll-stage-1`, until the history was reset on 2026-11-18

**Created**: 2026-11-14

**Status**: Done 2026-11-14 (retrospective, written 2026-11-27 from
`ATTIC/COLL-INPROGRESS/COLL-STAGE-1.md`): `just test` and `just full-test`
passed, `ansible-test sanity` included; merged into `develop`, released and
pushed on the operator's word the same day as the development version 0.2.0,
withdrawn 2026-11-18; its work is in 0.0.1, the first release (see
[CHANGELOG.md](../../CHANGELOG.md) and the Assumptions of
[specs/001-galaxy-publish/](../001-galaxy-publish/spec.md)).

**Input**: The operator asked whether the modules of the first development
version, 0.1.0 (`spack_env` and `spack_buildcache_push`, spec 007, being
written), are idempotent every time. The answer was "mostly". A repeat run
with nothing to do reported no change, against the real Spack v1.2.0 and in
the Cloud Sandbox's container test, but three things were not right:

1. `spack_env` regenerated the module files on every run, and with
   `delete_tree: true`, the default, deleted the tree first. The result was
   reported correctly, because the time Spack writes into each file was left
   out of the comparison. But the run was not a no-op: for a moment the
   module files were missing, and a user loading one then found nothing.
2. `spack_buildcache_push` with `force: true` pushed everything and reported
   a change on every run. That is what `--force` means, but nothing said so
   when it was left on.
3. `spack_buildcache_push` learned what it pushed by reading Spack's output,
   the `==> [n/m] Pushed <spec>/<hash>` lines of Spack v1.2.0. The module
   accepts any Spack from 1.0. If a later Spack printed those lines
   differently, the module would still push, but report no change.

This spec is a record of work done before this repository used Spec Kit. It
was written after the fact, and checked against the code as it is in 0.0.4.
Where later work changed what was built, a note names the later spec.

## Clarifications

### Session 2026-11-14

Asked one at a time, before the work began.

- Q: What should `spack_env`'s new option `refresh_modules` default to:
  `when_needed`, which changes what 0.1.0 did by default and makes a repeat
  run touch nothing, or `always`, which keeps 0.1.0's behaviour unless a task
  asks for the new one? → A: `when_needed`.
- Q: What counts as "needed": a stamp written after each regeneration (the
  lock, the modules configuration and the module trees), which also catches a
  change to the module configuration with nothing new to install and module
  files deleted or edited by hand; or only "this run concretized or installed
  something, or a root is missing", which needs no file of the module's own
  but misses both? → A: The stamp: the lock, the modules configuration, and
  the module trees.
- Q: What should `spack_buildcache_push` do about `force` left on: warn in
  the task's output on every run with `force: true`; add a new value,
  `force: once`, which overwrites only the packages no earlier run of the
  module on this node has overwritten, with `true` still overwriting all and
  warning; or change only the documentation? → A: The new value `once`;
  `true` still overwrites everything, and warns.
- Q: How should the module know what was pushed: ask the mirror, running
  `spack buildcache check` before and after the push, at the cost of two
  reads of the mirror's index per run; or keep reading Spack's printed lines,
  and only warn when the check before said something was missing and the
  lines name nothing? → A: Ask the mirror, before and after.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A repeat build touches no module file (Priority: P1)

A site's play runs `spack_env` with `modules: [tcl]` on every run. When
there is nothing new to concretize or install, and nothing about the module
files has changed, the run leaves every module file as it was: not deleted,
not rewritten. A user who loads a module while the play runs finds it.

**Why this priority**: it is the defect that started the work. A run that
deletes and rewrites files it then reports as unchanged is not a no-op, and
users of the node see the gap.

**Independent Test**: run `spack_env` twice with `modules: [tcl]` against the
real Spack; see the second run report `modules_reason: not_needed`, no
change, and every module file with the modification time it had.

**Acceptance Scenarios**:

1. **Given** an environment built and its module files regenerated by an
   earlier run, **When** `spack_env` runs again with the same input,
   **Then** no `spack module <system> refresh` is run, no change is
   reported, `modules_reason` is `not_needed`, and every module file keeps
   its modification time.
2. **Given** the same environment, **When** `spack_env` runs in check mode,
   **Then** it reports no change.
3. **Given** the same environment, **When** `spack_env` runs with
   `refresh_modules: always`, **Then** the module files are regenerated,
   `modules_reason` is `always`, and no change is reported, since only the
   time Spack writes into each file differs.
4. **Given** a run that concretized or installed something, **When** it
   finishes, **Then** the module files were regenerated, and
   `modules_reason` says `concretized` or `installed`.

---

### User Story 2 - Module files are put right when what they are made from changes (Priority: P1)

A site changes the `modules` configuration of an environment with nothing
new to install, or someone deletes or edits a module file by hand. The next
run regenerates the module files, as `always` would, and says why.

**Why this priority**: without it, "only when needed" would leave module
files wrong after any change that is not a new install. It is the reason the
operator chose the stamp over the simpler test (Clarifications).

**Independent Test**: after a first run, change the environment's `modules`
configuration, or delete one module file; run again and see the files
regenerated, with `modules_reason` `config_changed` or `files_changed`.

**Acceptance Scenarios**:

1. **Given** a changed `modules` configuration and nothing new to install,
   **When** `spack_env` runs, **Then** the module files are regenerated,
   `modules_reason` is `config_changed`, and a change is reported.
2. **Given** a module file deleted or edited by hand, **When** `spack_env`
   runs, **Then** the file is put back as Spack writes it, `modules_reason`
   is `files_changed`, and a change is reported; a further run reports
   `not_needed`.
3. **Given** a module file whose only difference is the time line Spack
   writes into it, **When** `spack_env` runs, **Then** that is not a change:
   `modules_reason` is `not_needed`.
4. **Given** a missing module root, **When** `spack_env` runs, **Then** the
   files are regenerated and `modules_reason` is `missing_root`.
5. **Given** a module file deleted by hand, **When** `spack_env` runs in
   check mode, **Then** it reports that the module files would change,
   `modules_reason` is `files_changed`, and the file is still missing
   afterwards.

---

### User Story 3 - What was pushed is known from the mirror (Priority: P2)

A site pushes an environment's packages to a build cache with
`spack_buildcache_push`. The task reports exactly the packages the mirror
gained, however Spack words its messages, and a second push reports no
change.

**Why this priority**: with the old way, a later Spack that worded its lines
differently would push and report no change, with no error. It is P2
because Spack v1.2.0, the pinned version, printed the lines the module read.

**Independent Test**: push to an empty mirror and see the packages the
mirror now has reported as pushed; push again and see no change; with the
stand-in `spack` wording its lines in another form, see the same.

**Acceptance Scenarios**:

1. **Given** a mirror that lacks some of the environment's packages, **When**
   the module pushes, **Then** `pushed` names exactly those the mirror
   lacked before and has after, and a change is reported.
2. **Given** a mirror that has every package, **When** the module runs again,
   **Then** nothing is reported as pushed and no change is reported.
3. **Given** a Spack that words its push messages differently, **When** the
   module pushes, **Then** what is reported is the same.
4. **Given** check mode, **When** the module runs, **Then** it asks the
   mirror once, pushes nothing, and reports what the mirror lacks.

---

### User Story 4 - Overwriting a mirror's packages once, and saying so when `force` is left on (Priority: P3)

A site rebuilt its packages with the same hashes and wants the mirror's
copies replaced, one time, without a task that pushes everything and reports
a change on every run after. A site that leaves `force: true` on is told,
every run, what that does.

**Why this priority**: `force: true` does what it says; the harm is a task
left that way, which is a smaller problem than the first three.

**Independent Test**: push, then push with `force: once` twice: the first
overwrites every package and reports them, the second reports no change.
Push with `force: true` and see every package reported and a warning in the
task's output.

**Acceptance Scenarios**:

1. **Given** packages already on the mirror, **When** the module runs with
   `force: once`, **Then** each is overwritten, reported as pushed, and
   recorded for that mirror.
2. **Given** a second run with `force: once` and nothing new, **When** it
   runs, **Then** nothing is overwritten and no change is reported.
3. **Given** a new package in the environment, **When** the module runs with
   `force: once`, **Then** only that package is overwritten.
4. **Given** `force: true`, **When** the module runs, **Then** every selected
   package is overwritten and reported, on every run, and the task's output
   carries a warning that says so and points to `force: once`.

---

### Edge Cases

- **Two environments under one module root.** Spack's default module root
  is shared by every environment of one Spack, and `--delete-tree` removes
  all of it. With two environments on the default root and
  `delete_tree: true`, each run would undo the other's, and the stamp would
  never match. This was found while writing the work (research R5). The code
  does not detect it; the option's documentation and the README say to give
  each environment its own root (`modules:default:roots`) or set
  `delete_tree: false`.
- **No stamp, an unreadable stamp, or one of another format version**: the
  module regenerates (`no_stamp`) and writes a stamp. A change is reported
  only if the files then differ. Deleting the stamp is safe.
- **A module system the stamp does not know** (one added to `modules`): the
  module regenerates (`no_stamp`).
- **`spack.lock` changed behind the stamp** (concretized by hand, outside the
  module): the module regenerates (`lock_changed`).
- **`modules` empty, or `state: concretized`**: nothing is regenerated, and
  `modules_reason` is `not_requested`.
- **Check mode** gives `modules_reason`, but reports the module files as
  changing only when that is certain: a missing root, or files changed by
  hand. For `concretized` or `installed` it cannot know what Spack would
  write; the run is reported as a change for those reasons anyway.
- **Only the time line differs** in a module file: never a change, in either
  mode of `refresh_modules`.
- **`force: once` and more than one mirror**: the record is kept per mirror
  URL (a mirror named by its Spack name is resolved to its URL first), so each
  mirror is overwritten once on its own.
- **The `force: once` record deleted or unreadable**: the next `force: once`
  overwrites every selected package once more. The README says deleting it is
  safe.
- **`force` given anything but true, false or once**: refused before any
  Spack command runs.
- **`force: true` in check mode**: every selected package is listed as what
  would be pushed. The warning is given only in a real run.
- **`only` and externals**: as in check mode before this work, externals are
  never counted, and `only` (`package` or `dependencies`) cuts the selection
  down, before and after the push alike.
- **A failed push** fails the task with Spack's message. The `force: once`
  record is not updated.
- **The environment removed with `spack env rm`**: the two files of the
  module's own go with it, as Spack removes its `.spack-env/` directory.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `spack_env` MUST take `refresh_modules`, `when_needed` (the
  default) or `always`. Any other value MUST be refused.
- **FR-002**: With `when_needed`, the module files of `modules` MUST be
  regenerated only when one of these holds, read in this order, the first
  naming the reason: this run concretized something new (`concretized`);
  this run installed something (`installed`); a module root is missing
  (`missing_root`); there is no usable stamp, or it does not cover every
  system in `modules` (`no_stamp`); `spack.lock` differs from the stamp
  (`lock_changed`); the merged `modules` configuration differs from the
  stamp (`config_changed`); a module tree differs from the stamp, the time
  line left out (`files_changed`). Otherwise no `spack module ... refresh` is
  run (`not_needed`). With `always` they MUST be regenerated on every run
  (`always`).
- **FR-003**: After regenerating, in either mode, the module MUST write its
  stamp, `.spack-env/csis_spack.modules.json` in the environment's directory:
  a digest of `spack.lock`, of the merged `modules` configuration, and of each
  module tree as it left it, with Spack's time line left out. The file MUST be
  replaced in one step, so that a stopped run leaves the old stamp or the new
  one.
- **FR-004**: The module roots MUST be read from Spack's own merged
  `modules` configuration for the environment, every scope merged, Spack's
  defaults included; `$spack` in a root is what `spack location -r` prints.
  (On Spack 1.0, which has no `config get --json`, the configuration is read
  through `spack python -c`: spec 003.)
- **FR-005**: `spack_env` MUST return `modules_reason` on every run: one of
  `always`, `concretized`, `installed`, `missing_root`, `no_stamp`,
  `lock_changed`, `config_changed`, `files_changed`, `not_needed`, or
  `not_requested` when `modules` is empty or `state` is `concretized`.
- **FR-006**: `modules_refreshed` MUST list only the module systems whose
  files changed, Spack's time line left out. The module files MUST count
  towards `changed` only when that list is not empty: regenerating files
  that come out the same is not a change.
- **FR-007**: In check mode `spack_env` MUST give `modules_reason`, MUST
  report the module files as changing only for `missing_root` and
  `files_changed`, and MUST NOT regenerate anything or write a stamp.
- **FR-008**: `spack_buildcache_push` MUST learn what it pushed from the
  mirror: `spack buildcache check` before and after the push, reporting as
  pushed what the mirror lacked before and has after, plus what `force`
  overwrote. Externals and `only` MUST be applied as in check mode. Spack's
  printed lines MUST NOT be read for this.
- **FR-009**: In check mode `spack_buildcache_push` MUST ask the mirror once,
  push nothing, and report what the mirror lacks, plus what `force` would
  overwrite.
- **FR-010**: `force` MUST take `false` (the default), `true` or `once`, and
  refuse anything else before running Spack.
- **FR-011**: With `force: true` the push MUST be given `--force`, every
  selected package MUST be reported as pushed on every run, and a real run
  MUST warn in the task's output that it overwrites every package and
  reports a change on every run, naming `force: once`.
- **FR-012**: With `force: once` the module MUST overwrite, by hash, each
  selected package it has not overwritten on that mirror before (`spack
  buildcache push --only package --force <mirror> /<hash>...`), then push
  normally; and MUST record the hashes it has overwritten, per mirror URL, in
  `.spack-env/csis_spack.pushed.json`. A run with nothing new to overwrite and
  nothing the mirror lacks MUST report no change.
- **FR-013**: The options' documentation MUST say what each value does,
  including that `force: true` and `refresh_modules: always` do work on every
  run. The `delete_tree` option and the README MUST say that Spack's default
  module root is shared by every environment of a Spack, and what to do
  about it (Edge Cases).
- **FR-014**: The README MUST say what the two files in `.spack-env/` are,
  that the directory is Spack's, that Spack leaves them alone and removes
  them with the environment, and that deleting either is safe.
  `CHANGELOG.md` MUST record the work.

### Key Entities

- **The module stamp** (`.spack-env/csis_spack.modules.json`): what the
  module files were last regenerated from. See
  [data-model.md](data-model.md).
- **The overwritten record** (`.spack-env/csis_spack.pushed.json`): which
  packages `force: once` has overwritten on which mirror URL.
- **`modules_reason`**: why the module files were regenerated, or why not.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Against the real Spack, a second run of `spack_env` with the
  default `refresh_modules` changes no file under the module roots: the same
  files, with the same modification times.
- **SC-002**: Against the real Spack, `spack_buildcache_push` reports
  exactly the packages the mirror gained, and a second push reports no
  change.
- **SC-003**: Against the real Spack, `refresh_modules: always` rewrites the
  module files without reporting a change; a deleted module file is put back;
  a changed modules configuration regenerates with nothing to install; and
  `force: once` overwrites one time.
- **SC-004**: Every value of `modules_reason`, both modes of
  `refresh_modules`, the stamp written, read and outdated (by a lock change, a
  modules configuration change, a module file deleted or edited by hand, and
  not by Spack's time line alone), the `force` warning, `force: once`, and the
  push reported from the mirror with the stand-in wording its lines in another
  form, are each held by a unit test against the stand-in `spack`.
- **SC-005**: `just test` and `just full-test` pass, `ansible-test sanity`
  on both modules included.

## Assumptions

- Spack leaves files it does not know in an environment's `.spack-env/`
  directory alone, and removes them with the environment (`spack env rm`).
  The plan said so and the README says so; the research records only that
  the directory exists as soon as the environment is concretized (R2).
- Two reads of the mirror's index per push run are an accepted cost: on S3,
  a few seconds.
- With `force: true` the mirror lacks nothing afterwards, so "pushed" is what
  was selected and pushed, as before.
- Changing the default from regenerating every run is acceptable, as the
  operator decided (Clarifications). A site that wants 0.1.0's behaviour sets
  `refresh_modules: always`.
- When this work was done, the collection was tested only against Spack
  v1.2.0. Spec 003 extended the integration tests to the real 1.0.0 and
  1.1.0, and found that every module that read the configuration with
  `config get --json`, `spack_env`'s module roots among them, failed on 1.0;
  it was fixed in 0.0.3 through the `BEHAVIOUR` table in
  [plugins/module_utils/spack.py](../../plugins/module_utils/spack.py).
- Spec 003 also added `yes_to_all` to both modules. It changes nothing here:
  `spack module ... refresh` is always given `-y`, and `spack buildcache
  push` and `check` list no `--yes-to-all`.
- The release was 0.2.0, a minor version for a new option and a changed
  default, with `CHANGELOG.md`, the modules' `version_added` and the README.
  It was withdrawn on 2026-11-18. The modules now carry `version_added: 0.0.1`,
  and `refresh_modules` and `force: once` none of their own, since they were
  in the first release.

### Out of scope

- **Moving the Cloud Sandbox to this version.** It is the Cloud Sandbox's
  work, in its own repository. Its `spack_environment` role passed
  `modules: [tcl]` and nothing else, so the new default would change what it
  did without a line changing there; that work was to set `refresh_modules`
  in the role's `spack_env` task explicitly and say why.
- **Known limitations, still open in 0.0.4**, taken up by spec 006
  ([specs/006-known-limits/](../006-known-limits/spec.md), done, not yet released):
  - `update_index: true` rebuilds the mirror's index on every run, and does
    not report it as a change.
  - Check mode's copy of the environment, made in a temporary directory, does
    not find files that `spack.yaml` names by a relative path (`include:`,
    `develop:`).
  - Spec 006 found the first not to be a limit: Spack rebuilds the index
    only after a push that sent something (its research, R1), and that is
    now documented and tested. It removed the second: the preview's copy now
    reads relative `include:` and `develop:` paths where they are (its
    FR-004).
- **Testing against Spack versions other than v1.2.0.** Out of scope then;
  done later by spec 003.
